# Cloudflare WARP on Lambda feasibility

## Scope and baseline

This experiment uses the official Cloudflare One Client in Local proxy mode inside a separate Lambda function. The production path is Codex Cloud’s built-in Tailscale VPN, the tagged Lambda Tailscale peer, raw TCP Serve on port 8443, and a loopback GOST CONNECT listener. The worker claims a `connect-v2` session in DynamoDB, validates the session token hash through GOST's loopback authentication hook, and pins global IPv4 addresses for the exact HTTPS allowlist. A resolver hook rejects any host-map miss. Tailscale and GOST exit on stop, failure, or expiry. The origin TLS session runs inside the CONNECT tunnel. The worker currently reports a direct `checkip.amazonaws.com` observation as `egress_ip`. The `vault` client verifies equality through its authenticated GOST tunnel and fails on mismatch.

The production AWS inspection on 2026-11-18 confirmed `us-west-1`, x86_64, 1,024 MiB memory, 512 MiB ephemeral storage, a 900-second timeout, no VPC subnets, and an Active function with a successful last update. CloudFormation returned `UPDATE_COMPLETE` and the Function URL lookup returned `ResourceNotFoundException`. The deployed digest is `sha256:4736921516d9bd2db09b1e0577fe47678214148da860edc16b699870af56988e`. All 18 bridge tests passed with the existing production build in a network-disabled, read-only container running as UID 1000. The Mac had Docker 29.7.2 with amd64 emulation and Terraform 1.17.2 for Darwin arm64.

## Package and runtime

The experiment used Cloudflare's stable EL9 x86_64 RPM, version 2026.8.2115.0. Its SHA-256 is `d6f0f6c56f35e5c7787385d807ebffc311e7aef40e52f59b069d030573074d15`. Amazon Linux's `rpmkeys` verified the RPM signature with key ID `4fa1c3ba` and the package digests. The RPM and key came from Cloudflare's official repository. The probe extracts the official daemon and CLI and installs their runtime dependencies from Amazon Linux. It skips RPM lifecycle scripts, which expect systemd and request file capabilities including `CAP_NET_ADMIN`. Both executables ran on Amazon Linux 2023 with glibc 2.34 and the required D-Bus, NSS and TPM2 libraries. Cloudflare's distribution support list does not include Lambda. [Official Linux releases and signing-key guidance](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/download/#linux)

The probe supervises the foreground daemon directly. It redirects state, logs and the CLI control socket to a private invocation directory on `/tmp` with `STATE_DIRECTORY`, `LOGS_DIRECTORY` and `RUNTIME_DIRECTORY`. It observed actual CLI responses in Docker and Lambda with no TUN device, zero effective capabilities, and a read-only root. A Docker attempt to launch a private session bus as an unknown numeric UID failed because D-Bus could not resolve the UID in the image's account database. The daemon still reached IPC readiness with the bus absent. This demonstrates startup without a D-Bus daemon. The unofficial wasque project was read for comparison. The probe does not use its artifacts or its bind-address rewrite. [Cloudflare client components](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/) · [wasque source](https://github.com/Diniboy1123/wasque)

Cloudflare requires MASQUE over HTTP/3/UDP for Local proxy mode. UDP/443 is the standard ingress, and Cloudflare lists additional UDP ports. HTTP/2 fallback is incompatible with Local proxy mode. Cloudflare documents a 10-second request limit, so captions, paginated history, and X/Reddit page reads need independent timing measurements under verified egress. Request latency and long-response behavior cannot be inferred from daemon readiness. [Client modes](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/modes/#local-proxy-mode) · [Cloudflare firewall requirements](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/firewall/#warp-ingress-ip)

## Enrollment and credential handling

Read-only Cloudflare inspection found the existing WARP enrollment app with an email-based Allow policy, one service token with no matching enrollment rule, default DNS-only client mode with MASQUE, and Gateway TLS decryption enabled at account level. The approved test used a dedicated one-hour Access service token and a Service Auth rule on just the enrollment app, matching just that token. The test did not change device profiles, Gateway settings, DNS or personal policies. TLS verification used the runtime’s public trust roots. The Mac's certificate bundle was mounted as a build secret only to allow verified access to the Amazon Linux package mirror. Local Docker's runtime direct-IP probe failed with the stock trust environment, while the real Lambda direct-IP probe succeeded.

The Lambda IAM role permits access to one temporary secret. `WARP_PROBE_SECRET_ARN` names that secret, whose JSON object has `organization` (the short Zero Trust team name), `client_id` and `client_secret`. The Python handler reads it before starting WARP. The WARP process does not inherit the Lambda role credentials. The handler writes a mode-0600 Linux MDM file under its `/tmp` state directory, with `service_mode=proxy`, `proxy_port=40000` and `warp_tunnel_protocol=masque`. Local MDM settings take precedence over profile settings. The probe discards daemon output after categorizing it and removes its state directory. For a long-lived deployment, device registration state would require an explicit lifecycle and isolation strategy. Independent cold sandboxes may enroll additional registrations, and `/tmp` can survive warm starts. [Headless enrollment](https://developers.cloudflare.com/cloudflare-one/tutorials/deploy-client-headless-linux/) · [MDM precedence and parameters](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/mdm-deployment/parameters/) · [Registration lifecycle](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/device-registration/)

## Invocation evidence

The temporary Lambda matched the production region, architecture, memory and storage. It used a 75-second timeout and a separate IAM role, private ECR repository and one-day test log group. The credential-free invocation ran as UID 993 on a read-only root with no TUN and zero effective capabilities. WARP answered IPC and accepted the Local proxy setting. Handler elapsed time was 5.21 seconds including its direct HTTPS check, billed duration was 5.48 seconds, AWS Init Duration was 272 ms and AWS reported peak memory of 163 MiB. WARP peak RSS was about 95 MiB and it used 28 threads. An explicit proxy request was refused before startup and after shutdown even though direct HTTPS worked. This tests the probe's no-fallback behavior. GOST is outside this image.

The first two enrolled invocations reached IPC, then timed out waiting for registration and the listener. Direct AWS egress worked. The handler measured 0.86 and 0.32 seconds from daemon launch to IPC. Peak Lambda memory was 201 and 203 MiB. The initial handler used a conventional XML plist wrapper. A controlled network-disabled container comparison with identical synthetic values found that WARP silently ignored the settings with the wrapper and loaded the bare dictionary shown in Cloudflare's Linux MDM documentation. The discriminator settings, a nondefault port and WireGuard, appeared in the effective settings only with the bare dictionary. The temporary Cloudflare enrollment policy and token were removed, Secrets Manager refused reads of the deleted secret, and no new registration appeared in the Cloudflare inventory. The separate test AWS resources were verified absent.

The corrected restricted Docker run applied the Linux MDM configuration and reported Local proxy mode and MASQUE. IPC became ready in 1.29 seconds. WARP ran for the connection window and never completed registration. Peak daemon RSS was about 122 MiB with 25 threads. The container used a read-only root, 512 MiB writable tmpfs, UID/GID 1000, no effective capabilities, no TUN device, 1 GiB RAM, a roughly 0.58 CPU quota, and limits of 1,024 processes and file descriptors. This is a local test under Docker Desktop emulation on an ARM Mac.

The first corrected Lambda invocation passed direct HTTPS but WARP did not respond to the CLI within the seven-second startup window. It shut down in 11.03 seconds with 181 MiB peak environment memory and a 321 ms AWS Init Duration. The correction and one bounded retry produced the following real Lambda evidence.

The retained classifier recorded `operation not permitted` and a connectivity-check marker after the corrected activation. It did not retain the failing syscall or connectivity stage, so this cannot establish whether a kernel operation, network policy, UDP path, or some other step blocked the tunnel. The deployed diagnostic checked for a listening proxy only after WARP reported Connected. The checked-in reproduction now samples the listener independently. Direct AWS HTTPS and enrollment establish outbound TCP reachability. MASQUE over outbound UDP remains unverified. The normal shutdown path was exercised. Sudden sandbox loss and device-state cleanup under hard termination were not exercised. The five diagnostic invocations were bounded and used temporary resources.

The replacement credential and its enrollment rule were removed, the one attributable registration was deleted and verified absent, and the Secrets Manager secret is no longer listed, including pending deletion. A final AWS read found zero test Lambda functions, ECR repositories, roles, log groups or secrets. The production digest was independently rechecked. Raw IPs and invocation results are under ignored `.codex/tmp/warp-feasibility/`. There is no effective Cloudflare IP to compare with the stored direct AWS IPs.

### Local follow-up

The existing macOS WARP session served as a reference. Its effective settings showed Local proxy mode and MASQUE. Explicit HTTP CONNECT to `127.0.0.1:40000` returned 200. HTTPS to the Cloudflare trace and AWS address-check endpoints returned 200 with certificate verification enabled. The public IP differed from the direct route and Cloudflare trace reported `warp=on` and `gateway=on`.

The separate Linux Docker retest reused the restricted x86_64 image and enrolled with its own approved one-hour service token. CLI IPC was ready in 1.29 seconds. The CLI confirmed enrollment, active MDM, Local proxy mode and MASQUE. An explicit `warp-cli connect` returned success, while status reported `Unable` throughout the 65-second connection window. Independent TCP checks never found the proxy listening on port 40000. The daemon logged `operation not permitted` from `warp_connection::forward_proxy`. This identifies the Linux subsystem involved. The specific denied operation is still unknown, and the earlier Lambda diagnostics did not retain the subsystem. The Docker run itself completed verified direct HTTPS.

Only the Linux Docker test created a registration. The daemon shut down and removed its temporary state, and the test registration, service token and enrollment policy were removed and their absence verified. The test created no AWS resources.

## Gate outcome and production rollback

The real Lambda feasibility gate failed at the tunnel and data path after enrollment. The server integration, Terraform setup and plan, client contract changes, and production deployment remain gated. No signed-out caption comparison, authenticated history check, or Cloud-to-Cloudflare YouTube, X or Reddit acceptance was run. The existing tests cover the deployed direct mode. The unsigned Cloud/VPN outcomes for that mode remain documented in the server guide.

A future approved test should retain only safe operation names and connectivity-state transitions from the daemon and distinguish QUIC ingress reachability from local runtime permission errors. Any candidate must complete CONNECT and verified origin HTTPS through the listening proxy, check the direct and proxied public IPs, and demonstrate WARP and Gateway use with the Cloudflare trace flags or correlated test-device activity. Account-wide TLS inspection is enabled in this account. A production design must verify that traffic from just the service identity can preserve origin TLS without inspection, with no account-wide policy change. [Cloudflare troubleshooting](https://developers.cloudflare.com/cloudflare-one/troubleshooting/warp-client/) · [Gateway activity logs](https://developers.cloudflare.com/cloudflare-one/insights/logs/dashboard-logs/gateway-logs/)

There is no production rollback to perform for these tests. For a future rollout, capture the current CloudFormation template and existing parameter references and retain the original image by digest before approval. To roll back, deploy the previous template and digest to the same `service-bridge` stack with the existing Tailscale secret reference and Cloud role setting. Use the baseline digest in this report if it is still the approved direct-mode version. Confirm the change set preserves the existing DynamoDB session table, then verify Active/Successful, the restored digest and absence of a Function URL. Use a fresh direct-mode `connect-v2` session to confirm private 407, CONNECT, origin TLS, matching egress and shutdown. Close any active Cloudflare-mode sessions before switching. Keep the existing DynamoDB table and client-owned cache data in place. A rollback change set should never use stack deletion to restore an image.

## Persistent Linux gateway alternative

Keep the Lambda service, Tailscale ingress, `connect-v2` and GOST. Run official WARP on a supported Linux host with persistent encrypted storage and a dedicated device identity. Bind WARP only to loopback. Expose a separate authenticated upstream proxy only over that host's Tailscale interface. Grant the Lambda service tag access to just that upstream port and deny ordinary public inbound traffic. Since Lambda's Tailscale daemon uses userspace networking, the Lambda-side upstream client would need an explicit path through its local Tailscale SOCKS endpoint or another supported userspace socket path. A regular IP socket dialing a tailnet address is insufficient in that configuration.

Use TLS with mutual authentication or an equivalent private authenticated hop for Lambda-to-gateway, and enforce exact destination and port checks. Validate the actual forwarding semantics before selecting the implementation. GOST must check the requested host and TCP 443, resolve it once to a vetted public IP, and convey that selected IP through the upstream chain while leaving the original TLS SNI and certificate verification to the client. Verify the gateway and WARP accept a CONNECT to a pinned IP and that no hop re-resolves an unchecked hostname. If that cannot be demonstrated, reject this design. Keep AWS and cache management calls off the upstream path. Treat unavailable WARP, upstream failures, or a verified-egress mismatch as session failures. A gateway could also use supported transparent WARP routing on just the upstream process or its network namespace if Local proxy's request limit or IP-literal CONNECT makes the first option unsuitable. Verify management routing, DNS ownership, and private-node reachability separately for that variant.

A persistent Linux host avoids enrolling a new WARP instance in each Lambda sandbox, moves WARP updates and device state to one machine, and adds a separate network hop and always-on maintenance. Monitor verified HTTPS and effective egress, patch the OS and client, rotate enrollment credentials, bound policy logging, and account for single-host downtime. A persistent gateway still needs an approved end-to-end validation and its own provisioning approval.

## Reproduce the standalone image

Run from the root of the `service-bridge` checkout. The production Dockerfile has its own allowlisted context.

```bash
umask 077
work="$PWD/.codex/tmp/warp-feasibility/repro"
mkdir -p "$work"
cp infra/service-bridge/experiments/warp/{.dockerignore,Dockerfile,probe.py} "$work/"
curl -fsSL https://pkg.cloudflareclient.com/pubkey.gpg -o "$work/cloudflare-warp.gpg"
curl -fsSL https://pkg.cloudflareclient.com/rpm/9/x86_64/cloudflare-warp-2026.8.2115.0-1.el9.x86_64.rpm \
  -o "$work/cloudflare-warp.rpm"
docker build --platform linux/amd64 --provenance=false -t service-bridge-warp-probe:repro "$work"
docker run --rm --platform linux/amd64 --read-only \
  --tmpfs /tmp:rw,nosuid,nodev,mode=1777,size=512m \
  --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges \
  --memory 1g --cpus 0.58 --pids-limit 1024 --ulimit nofile=1024:1024 \
  --entrypoint python service-bridge-warp-probe:repro -B /var/task/probe.py \
  > "$work/local.json"
```

If the Docker build uses a trusted local outbound TLS proxy, pass its trusted CA bundle as `--secret id=hostca,src=/path/to/ca-bundle.pem` on the build command. The bundle is mounted only for package downloads and is not copied into runtime trust. The credential-free test sets proxy mode without creating any registration. For an approved local enrollment, pipe the same three-field JSON from a trusted secret retrieval process into Docker with `-i --env WARP_PROBE_SECRET_ARN=local-stdin`. Leave output redirected into ignored private storage.

For an approved Lambda retest, use an isolated temporary image repository, IAM role and Lambda in `us-west-1` and an explicit synchronous `{}` invocation. The credential-free role needs log writes only. For enrollment, scope `secretsmanager:GetSecretValue` to the temporary secret, and set `WARP_PROBE_SECRET_ARN` to its ARN. Capture the response and AWS report locally and redact network identity values before sharing. Force no public ingress and make cleanup independent of the probe result. Stop the daemon before revoking the temporary enrollment policy and deleting the test registration, then remove the token, secret and test AWS resources. The production deploy script and Terraform state are outside this experiment.
